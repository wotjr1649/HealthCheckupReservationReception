### 2.1 실측으로만 알 수 있었던 것

이것들은 문서에 없고 재 봐야 나온다. 같은 자리를 다시 밟지 마라.

```text
CheckedComboBoxEdit 을 못 쓴다
  QueryDisplayText 가 그 클래스에서 "not supported" 다 — 표시글을 고정할 수 없다
  → PopupContainerEdit + PopupContainerControl + CheckedListBoxControl 로 간다

RepositoryItem 의 CheckState 는 사용자 체크를 따라오지 않는다
  Designer 가 적어 둔 처음 값일 뿐이다. 지금 켜진 것은 체크 목록 컨트롤에만 있다

SimpleButton.PerformClick() 은 안 뜬 폼의 버튼에서 아무 일도 안 한다
  시험에서 클릭을 흉내 내려면 Designer 가 이름으로 잇는 핸들러를 직접 불러야 한다

가로 스크롤은 컬럼 폭으로 서지 않는다
  OptionsView.ColumnAutoWidth 기본값이 true 라 컬럼을 뷰 폭에 욱여넣는다
  (실측: 컬럼폭합 3000 · 뷰폭 1140 인데 가로 스크롤 숨김)
  → auto 를 끄면 컬럼이 적을 때 빈 공간이 남는다. 켠 채로 컬럼마다 MinWidth 를 준다

서비스를 생성자로 받는 화면은 VS 디자이너가 못 연다
  「디자이너에 대한 문서를 로드하지 않았으므로 디자이너를 표시할 수 없습니다」
  → 디자이너가 설계 대상을 매개변수 없는 생성자로 만들기 때문이다. 셋이 그랬다
    (MainForm · FrmPatientEditor · FrmPatientSelect). 컴파일도 시험도 통과하므로
    디자이너를 여는 사람만 만난다
  → **새 화면(WF-RSV-01 · WF-WRK-01)에도 반드시 단다.** MainFormTests 의
    `모든_화면이_디자이너용_생성자를_갖는다` 가 이제 이것을 잰다

LayoutControl 은 한 줄 안의 라벨 폭을 가장 긴 것에 맞춰 통일한다
  `예약/접수일` 옆의 `~` 한 글자짜리 라벨까지 그 폭을 떠안고, 그만큼이 입력칸에서 깎인다
  (실측 2026-09-10: 종료일 DateEdit 이 54px 로 눌려 잘린 채 사용자에게 보고됐다)
  → 항목마다 `TextAlignMode = TextAlignModeItem.AutoSize`
  → **라벨 길이가 제각각인 줄에서만 드러난다.** WF-PAT-01 은 라벨 셋이 전부 같은 폭이라
    이 함정을 밟은 적이 없다 — 그 화면을 본떴다고 안전한 것이 아니다
  → 세로로 쌓인 상세 그룹에서는 반대로 그 통일이 필요하다(`AlignWithChildren`).
    끄고 켜는 기준은 "한 줄인가 한 열인가" 다

캡션 그룹의 폭은 안에서 가장 넓게 못 박힌 항목이 정한다
  `예약일` 칸 하나를 MaxSize 300 으로 묶었더니 `예약 일정` 그룹 전체가 600 → 330 으로
  줄어 옆 칸의 차단 사유가 잘렸다(실측 2026-09-11). 상단 45:55 도 함께 무너졌다
  → 그룹 안에서 **폭은 묶지 않는다.** 높이만 묶고 폭은 그룹 크기에 맡긴다
  → DLG-PAT-03 의 "그룹 안쪽 폭이 그룹 폭보다 작다" 와 같은 뿌리다 — 캡션·테두리가
    있는 그룹은 안팎의 폭이 다르고, 둘을 서로 맞추려 들면 어느 쪽이든 어긋난다

RadioGroup 은 항목을 제 높이에 고르게 편다
  자리를 넉넉히 주면 오전과 오후 사이가 손가락 두 개만큼 벌어져 한 묶음으로 안 읽힌다
  → 줄 수만큼만 높이를 묶는다. 남는 세로는 아래 영역이 가져간다

성공한 0건과 실패는 화면에서 같은 그림이다
  빈 Grid 는 고장과 구별되지 않는다 — 예약접수 0행인 DB 에서 조회가 정상 성공했는데
  "조회가 안 된다" 로 보고됐다(실측 2026-09-10). SP 는 성공여부=1 · 0행을 냈다
  → Grid 빈 자리에 이유를 적는다 (`clsGridColumns.ShowEmptyText`)
  → 조회 실패는 모달이 아니라 Inline 이다. 모달이면 창을 열자마자 뜨는 것을 막느라
    조용히 삼켜야 하고, 그러면 실패가 아예 보이지 않는다
```

### 2.2 LayoutControl 은 "어떤 배율이든 같은 x,y" 가 아니다

```text
                  100%          150%
lci Min/MaxSize   190×26   →    285×39      정확히 ×1.5
lci Bounds        X=110    →    X=165       정확히 ×1.5
```

**픽셀은 배율에 정비례해 커진다.** 고정되는 것은 논리 좌표(DIP)와 배치 관계다. 못 박은
`MinSize`/`MaxSize` 도 함께 커지므로 고배율에서 잘리지 않는다 — 절대좌표였으면 잘렸을
자리다. **150% 모니터 실측 완료(2026-09-10 사용자) — 폰트까지 정상이다.**

### 4.6 예약을 모달로 — 2026-09-10 grilling 2회차

```text
1. 신규 예약은 모달이다. 신규예약 · 예약변경 · WalkIn 이 같은 모달 하나를 쓴다
2. 리본 [신규 예약] Page 는 휴무일 방식으로 남는다 — 고르면 모달을 열고 직전 Page 로 돌아간다

```

**왜 모달인가 — 근거 셋.**

```text
같은 화면이 이미 두 벌로 설계돼 있었다
  03 §8.3 WF-RSV-01 과 §10.1 DLG-RSV-01 은 내용이 같다. 우연이 아니다 — 05 §9.3 이
  신규 일반예약 · 신규 WalkIn · 예약변경 **셋을 SP-RSV-01 하나로** 받게 했고, §9.4 의
  `변경범위`(ALL/SLOT/EXTRA/SLOT_EXTRA/NONE)가 있는 이유가 "한 호출자가 셋을 다 한다" 다.
  탭 하나 + 모달 하나로 만들면 ROOT AGENTS.md §6 이 두 번 물렸다는 그 함정이다

탭의 이점이 2026-09-10 에 이미 없어졌다
  탭 스트립을 걷으면서(§2) 「작성 중에 딴 화면 갔다 오기」가 사라졌다. 그 부작용이 §4.3 의
  「미저장 신규예약이 보이지 않는 문제」이고 §6 5번은 그 증상을 상태바로 때우려던 것이다.
  모달이면 문제 자체가 없다 — **§6 5번이 사라진다**

진입점 셋 중 둘이 이미 수검자를 들고 온다
  모달은 "부른 쪽이 대상을 준다" 는 그 모양이다. 그래서 모달 안에 [수검자 선택] 을 두지
  않는다 — 수검자를 바꾸려면 닫고 다시 연다. §8.10 Reset 이 자동이 된다
```

**조회조건 다섯으로 되돌아온다.** `03` §7.2 는 DLG-PAT-02 의 조회계약이 WF-PAT-01 과 같다고
적었는데 **코드는 각자 가지고 있었다.** 둘을 같은 부품 위에 올리면서 조건을 다섯
(차트번호·이름·주민번호·생년월일·휴대전화)으로 두고 기본은 앞 셋만 켠다 — 2026-09-10 에
걷은 둘이 「끌 수 있는 조건」으로 돌아오므로 **§5 가 적어 둔 `01` P01-01 · `02` F-PAT-001
과의 이탈이 닫힌다.** `SP-PAT-01` 은 그 둘을 처음부터 받고 있었다 (05 §7.2).

### 4.7 리본은 명령이지 내비게이션이 아니다 — 2026-09-11 사용자 지적

사용자가 「기능 배치가 다 이곳 저곳 중구난방」이라 보고했다. 뿌리는 하나였다:
**탭 다섯 중 셋은 「가는 곳」이고 둘은 「하는 일」이었다.**

```text
수검자 관리 · 예약 관리 · 접수 관리   눌렀다 → 화면이 바뀐다     장소
신규 예약   · 휴무일 관리             눌렀다 → 모달만 뜨고 되돌아온다  명령
```

같은 띠에서 어떤 것은 가고 어떤 것은 뜨니 예측이 되지 않는다. MSDN 이 이 실패를 이름
붙여 놨다 — *"The Ribbon seems to magnify bad navigation design … you should not adapt it
blindly for your application as a navigation mechanism."*
(<https://learn.microsoft.com/en-us/archive/msdn-magazine/2009/march/usability-in-practice-strategies-for-designing-application-navigation>)

그 아래 증상 셋이 전부 이 하나에서 나왔다:

```text
(a) [신규예약] 이 두 곳에 있었다 — 수검자 관리 Action 과 리본 Page
    리본 UX 가이드가 명시적으로 금지한다: "Present each command on only one tab.
    Avoid multiple paths to the same command … when users find what they are looking
    for, they stop looking."
    (https://learn.microsoft.com/en-us/windows/win32/uxguide/cmd-ribbons)
    게다가 둘의 동작이 달랐다 — 하나는 대상이 이미 있고, 하나는 고르는 창을 더 띄웠다

(b) DLG-PAT-02 가 WF-PAT-01 의 복제였다 — 같은 조회조건 다섯, 같은 Grid, 같은 컬럼

(c) 업무 순서가 거꾸로였다. 01 P01 은 「수검자를 찾는다 → 그 사람을 예약한다」인데
    리본 [신규 예약] 은 「예약을 시작한다 → 사람을 찾는다」로 들어갔다
    **거꾸로 들어갔기 때문에 사람 찾는 화면이 하나 더 필요했던 것이다** — (b)는 (c)의 결과다
```

**결정 (A안).** 리본을 명령 전용으로 되돌린다.

```text
Page 는 「가는 곳」만 갖는다        수검자 관리 · 예약 관리 · 접수 관리 — Page ↔ 화면 1:1
[신규 예약] Page 삭제              진입점은 수검자 관리 > [신규예약] 하나
[휴무일 관리] Page → 버튼          RibbonControl.PageHeaderItemLinks (탭 줄 오른쪽 끝)
DLG-PAT-02 는 WalkIn 전용          접수 관리 > [현장 당일예약] 만 이것을 연다
```

`MainPresenterTests.상단_Navigation_은_하나도_빠짐없이_업무_화면을_세운다` 가 이것을
문장이 아니라 게이트로 잡는다 — `BusinessNavigation` 전체를 돌며 「가지 않는 Page」를
찾는다 (ROOT AGENTS.md §6).

곁가지로 `MainPresenter._lastBusinessPage` 가 사라졌다. 휴무일 Page 에서 돌아올 자리를
기억하던 값인데 휴무일이 Page 가 아니게 되면서 읽는 곳이 없어졌다 — 쓰기만 하는 상태다.

### 4.8 개발 중에는 업무시간을 열어 둔다 — 2026-09-11

업무 가능 판정(`308`·`309`)과 마감시각은 전부 DB `운영기준` 한 행이 갖는다(R13). 코드로
우회할 자리가 없으므로 **데이터를 연다.** 시험용 예약을 SP 로 넣어 둔 것과 같은 부류다.

```sql
-- 열기 (지금 상태)
UPDATE dbo.운영기준 SET 운영시작시각='00:00:00', 운영종료시각='23:59:59',
  일반예약AM마감='23:59:00', 일반예약PM마감='23:59:00',
  접수AM마감='23:59:00', 접수PM마감='23:59:00' WHERE 기준ID=1;

-- 되돌리기 (배포 원본값)
UPDATE dbo.운영기준 SET 운영시작시각='09:00:00', 운영종료시각='18:00:00',
  일반예약AM마감='10:00:00', 일반예약PM마감='15:00:00',
  접수AM마감='11:00:00', 접수PM마감='16:00:00' WHERE 기준ID=1;
```

`[!]` **인수 전에 반드시 되돌린다.** 열어 둔 채로는 마감시각 규칙(03 §8.6)을 한 번도
실측하지 못한다 — 지금 그 길은 시험되지 않은 상태다.

### 4.9 예약 진입점 재설계 — 2026-09-11 grilling

사용자가 셋을 물었다: 예약 가능한 수검자를 어떻게 아는가 · 현장 당일예약을 수검자 쪽으로
가져오는 것이 좋지 않은가 · 계약을 깨야 한다면 어디를 깨는가. 인터뷰 결과는 이렇다.

**뿌리는 `00` RP-05 다.**

> 예약 없이 현장 내원한 경우 **당일예약 마감 전에는 일반 당일예약으로**, 당일예약 마감
> 이후부터 접수 마감 전까지는 **`WalkIn` Context의 현장 당일예약으로** 먼저 예약을 생성한다.

같은 사람이 09:30 에 오면 `NORMAL`, 10:30 에 오면 `WALKIN` 이다. **다른 업무가 아니라 같은
업무의 시각대 차이**이므로 버튼이 둘이면 조작자가 시계를 대신 읽는다.

```text
[예약] 하나                     수검자 관리에서만 들어간다. 접수 관리의 [현장 당일예약] 제거
예약구분은 DB 가 고른다          일반으로 묻고, 304 마감경과로 막히면 현장으로 한 번 더 묻는다
DLG-PAT-02 삭제                 대상 없이 여는 자리가 0 이 되었다 — 화면 하나가 통째로 사라졌다
저장 후 착지는 날짜로 가른다     오늘이면 접수 관리, 미래면 예약 관리
[신규예약] → [예약]              WalkIn 이 합류하면 "신규"가 거짓이 된다
```

`[!]` **오늘인지를 화면이 재지 않는다.** `database/deploy/03_Functions.sql` 이

```sql
[적용마감시각] = CASE WHEN @예약일 = b.[오늘날짜] THEN b.[기본마감시각] ELSE NULL END
```

이므로 **마감시각이 채워져 있다는 것이 곧 그 날이 DB 오늘날짜라는 뜻**이다. PC 시계도,
오늘날짜를 얻으려는 추가 조회도 필요 없다. 두 판정(예약구분·착지)이 같은 단서를 쓴다.

### 4.11 예약 가능 여부는 화면에서 이어 붙인다

`SP-PAT-01` 의 RS1 아홉 칸은 전부 수검자 기준정보다 — **목록은 예약을 모른다.** 계약과 배포가
동결이라 컬럼도 필터도 붙일 수 없다. 그런데 `SP-WRK-01` 의 RS1 에 `수검자ID` 가 있다:

```text
| 업무ID | 수검자ID | 예약일 | 시간대코드 | 상태코드 | 상태명 | 성명 | 차트번호 | ... |
```

그래서 **계약을 열지 않고 화면에서 이어 붙인다.** 조회할 때 두 번 더 묻는다:

```text
RSV  날짜 없이 전건   과거 미접수까지 봐야 상세에 그것을 적는다. 남는 양이 작다
RCP  오늘 것만        접수는 당일 업무라(05 §8.2 START_RECEPTION) 유효한 RCP 는 오늘뿐이고,
                     날짜를 안 걸면 완료된 접수가 세월과 함께 쌓인다
```

가르는 규칙은 `00` RP-06 하나이고, 그 문장이 화면에 한 번 더 적히므로 상태코드를
`Common/DbWorkStatus.cs` 로 모으고 `scripts/verify-work-status.sh`(WKS-001)가 05 §2.2 와
대조한다 (ROOT AGENTS.md §6). 넷은 이미 `UcWorkbench.UI.cs` 에 문자열로 박혀 있었다 —
거기서는 틀려도 조용했지만, `예약 가능/불가` 가 같은 값을 쓰기 시작하면 **잘못된 판정**이 된다.

```text
목록 컬럼 `예약`   가능 / 불가 — 훑는 자리라 두 값이다
상세 `예약 상태`   예약 불가 — 2026-09-14 오전 예약
                  예약 가능
                  예약 가능 (지난 예약 09-05 오전 미접수)
조회조건 여섯째    예약 없는 수검자만 — SP 로 가지 않고 화면이 거른다. 기본은 꺼짐
```

`[!]` **이어 붙이지 못하면 칸을 비운다.** 업무 조회가 실패했는데 `가능` 이라 적으면 거짓이
되고, 사용자는 예약을 걸었다가 모달에서 막힌다. 오늘날짜도 PC 시계에서 얻지 않는다 —
창구 PC 가 하루 어긋나면 예약 가능한 사람이 불가로 보인다.

### 4.10 과거 미접수 건 — 계약이 이미 정해 놓았다

`00` RP-06: *"중복판단 유효예약은 `예약일 >= DB 현재일` … **과거 업무는 중복판단에서
제외한다.**"* 그래서 과거 RSV 가 남아 있어도 새 예약은 정상 저장된다 — 버그가 아니다.
`05` §8.2 의 `START_RECEPTION` 이 `RSV + 예약일=오늘` 이라 **접수도 DB 가 이미 닫는다.**

남는 것은 「보이지 않는다」 하나다. `01` §7 은 상태전이 셋뿐이고 *"순환 상태전이와 복원
경로는 없다"* 이며 `05` §2.2 상태코드도 넷뿐이라 **노쇼를 표현할 코드가 없다.**

`상태=RSV` **그리고** `예약일<오늘` — 이 두 값의 조합이 곧 미접수 경과다. 새 상태코드 없이
읽힌다. 정리는 이미 열려 있는 `[예약취소]`(RSV→CNR)로 한다.

`[!]` **`NOS` 상태를 만들지 않기로 했다.** `00`·`01` 동시 재봉인이고 `01` 이 *"신규 업무분기나
역방향 상태전이를 추가하지 않는다"* 를 명문으로 금지한다. 결정적으로 **이 DB 는 SQL Express
라 SQL Server Agent 가 없어 자동 만료를 돌릴 자리가 아예 없다.**

### 4.12 휴무일 관리는 Modal 이 아니라 업무 화면이다

`03` §24 는 `DLG-HOL-01` 을 Modal 로 적었다. 2026-09-11 사용자 지시로 **넷째 탭 업무 화면**이

되면서 `접수 관리` 오른쪽에 자리가 생겼다. ROOT `AGENTS.md` §1.1 이 배치·내비게이션을 풀었고
아직 미구현이라 되돌릴 비용도 없었다.

**화면 ID 는 `DLG-HOL-01` 그대로다** — `WF-RSV-01` 이 모달이 될 때와 같은 처리이고,
`verify-ui-db-matrix.sh` 가 보는 ID 목록이 green 으로 남는다.

`03` §24 의 업무 규칙은 전부 그대로 산다:

```text
§24.4  법정·대체 행은 회색 + 선택해도 입력행에 싣지 않는다 (RowStyle · Pick)
§24.5  [추가]는 늘 열려 있고 [수정]·[삭제]는 자체휴무일 행이 잡혔을 때만 열린다
       휴무일자는 PK 라 수정에서 바꾸지 않는다 — 잡아 둔 행의 날짜로 보낸다
§24.6  잔여일수 < 경고임계일수 만 비교한다 — **임계 숫자를 화면이 갖지 않는다**
§24.2  공통 업무조건(308·309)이 이 화면에는 걸리지 않는다 — SP 가 애초에 내지 않는다
```

`[!]` **조회기간 기본값에 `00` §7.4 의 달력 날짜를 옮겨 적지 않았다.** 같은 값이 두 곳에
생기고 이 자리에는 그것을 지킬 게이트가 없다 (ROOT `AGENTS.md` §6). 화면 기본값은
「DB 오늘날짜부터 두 해」라는 **상대 범위**이고, 등재가 언제 끝나는지는 SP 가 RS2 로 말해 준다.

`휴무구분` 세 값은 화면이 판정에 쓴다(편집 잠금·회색 표시). `Common/DbHolidayType.cs` 로 모으고
`scripts/verify-holiday-type.sh`(HOT-001)가 배포된 `01_Schema.sql` 의 `CK_휴무일_TYPE` 제약과
양방향으로 대조한다 — 05 는 세 값을 한자리에 나열하지 않고, 실제로 강제하는 곳이 그 CHECK 한
줄이며 `verify-db-frozen.sh` 가 그 파일을 얼려 둔다.

곁가지로 §4.7 에서 켰던 Application 버튼(`[관리]`)이 다시 꺼졌다 — 거기 둘 것이 없어졌다.
