# 테스트 시나리오 및 결과 (2026-09-14)

과제 브리프 §7 「직접 테스트 시나리오를 작성하여 정상적인 업무 흐름과 예외 상황을 검증한다」와
§9 최종 산출물의 마지막 줄이 이 문서다.

**결과 칸은 손으로 적지 않는다.** S01~S07 은 실물 DB 에 붙어 도는 시험이고, 아래 표의 「증거」가
그 시험 이름이다. 다시 돌리는 법은 §4 에 있다.

```text
층      Service → Repository → Stored Procedure → 실물 DB
아닌 층 화면 픽셀. 그쪽은 단위시험 277건과 실행 화면 캡처가 맡는다 (§3)
```

## 1. 정상 업무 흐름 — 브리프 §3

브리프가 그린 줄은 하나다: **수검자 등록 → 검진 예약 → 예약 조회 → 수검자 내원 → 접수.**

| ID | 시나리오 | 기대 | 결과 | 증거 |
|---|---|---|---|---|
| S01 | 새 수검자를 등록하고, 오늘 열린 시간대로 예약하고, 목록에서 찾고, 접수한다 | 결과코드 0 · 상태 `RSV` → `RCP` | **PASS** | `ScenarioDbTests.S01_등록에서_접수까지_한_흐름으로_통한다` |

한 시험이 네 단계를 잇는 것은 **단계 사이의 값이 실제로 흘러야** 하기 때문이다 — 등록이 준
`수검자ID` 로 예약하고, 예약이 준 `업무ID`·`행버전` 으로 접수한다. 단계를 쪼개면 그 이음매가
시험되지 않는다.

## 2.5 화면 증빙 — 브리프 §9 (2026-09-15)

브리프 §9 가 화면 측 증빙을 요구한다. 위 시나리오 중 넷을 **실물 DB 에 붙은 화면**으로 다시
밟아 단계마다 떴다. 산출물은 `docs/phase5/output/screens/` 다.

`[!]` **주입한 그림이 아니다.** 조건 칸에 차트번호를 넣고 `[조회]` 를 실제로 누른 뒤, 사용자가
행을 고르는 그 지점을 그대로 부른다(`clsGridRowPicker.Select`). 값을 화면 뒤로 밀어 넣으면
그림은 같아 보여도 아무것도 증명하지 못한다 — **조건 칸이 빈 채 결과만 있는 그림**은 받는
사람에게 「조회도 안 했는데 결과가 있다」로 읽힌다.

전·후 두 장은 **같은 조건**이다. 그 수검자의 차트번호 하나로 좁히므로 다른 시험이 만든 줄이
섞이지 않는다.

| 시나리오 | 화면 | 무엇이 보이는가 |
|---|---|---|
| S01 | `s01_1_예약전.png` | 예약 관리 · 그 차트번호로 조회 · **0행**. 뒤 석 장의 기준이다 |
| S01 | `s01_2_수검자등록.png` | 수검자 관리 · 방금 등록한 그 사람 1행과 상세 |
| S01 | `s01_3_예약후.png` | 예약 관리 · 같은 조건에 **예약완료** 한 줄이 생겼다 |
| S01 | `s01_4_접수후.png` | 접수 관리 · 같은 줄의 상태가 **접수완료** 로 옮겨졌다 |
| S03 | `s03_예약취소후.png` | 예약 관리 · 줄은 남고 상태만 **예약취소** 다 — 물리삭제하지 않는다 |
| S04 | `s04_재접수시도후.png` | 접수 관리 · 재접수가 `502` 로 막힌 뒤에도 **접수완료 그대로** 다 |
| S05 | `s05_접수취소후.png` | 접수 관리 · **접수취소** 다 — 예약으로 되돌아가지 않는다 |

`[X]` **접수 상태 업무는 예약 관리 탭에 나타나지 않는다** (`03` §9.1 — Context 가 상태 목록을
정한다). 그래서 접수 뒤의 석 장은 접수 관리 창구다. 값을 화면 뒤로 밀어 넣던 초판은 이
필터를 건너뛰어 그 사실을 감췄다.

`[X]` **두 창구는 조회기간도 다르다.** 접수 관리는 `오늘 ~ 오늘` 로 서고 예약 관리는 종료일
없이 `오늘 ~` 로 선다 — 접수는 당일 건만 처리하고(`00` RCP-02) 예약은 앞으로의 날짜를 보기
때문이다. 그림 여섯의 종료일 칸이 서로 다른 것은 그 때문이며, **비일관이 아니라 창구가 다른
것**이다.

`[X]` **S02·S06·S07 은 그림이 없다.** 셋은 화면이 아니라 **저장이 막히는 것**이 증거이고
(중복 등록·필수값 누락·중복예약), 막힌 순간의 화면은 조작 직전과 같다. 그 자리는 시험 결과가
맡는다.

`[X]` **예외를 대화상자로 뜨지 않는다.** 화면 메시지는 전부 Modal 이라 시험 스레드가 그 순간
그림을 뜰 수 없고, 무엇보다 막혔다는 증거는 문구가 아니라 **아무것도 바뀌지 않았다는 것**이다.

다시 뜨는 법 — §4 의 명령에 이어서 돌린다.

```bash
cd winforms
"$VST" tests/HealthCheckupReservationReception.Tests/bin/Debug/HealthCheckupReservationReception.Tests.dll \
       /TestCaseFilter:"FullyQualifiedName~ScenarioCaptureTests"
node tools/build-scenario-evidence.js      # 산출물로 옮기고 빠진 것을 잡는다
```

`[!]` 그림은 `winforms/artifacts/logs/scenario/` 에 뜨고 그곳은 `.gitignore` 대상이다.
**산출물로 옮기는 것은 생성기가 한다** — 위 표가 가리키는 파일이 없거나 비어 있으면 `exit 1`
이고, 표에 없는 그림은 산출물에서 지운다. 표가 목록의 단일 출처다.

### 3.1 대상판정과 성별 (2026-09-14 실측)

점검용 수검자에 **과거 검진 완료이력과 나이대**를 심고 나서야 갈라진 갈래들이다.
심는 법과 이유는 `winforms/scripts/seed-tgt-cases.sh` 가 갖는다.

```text
차트   성별 나이  TGT사유  최근완료      NEX  조건부
D0011  M   40      0      -            10   NEX-02,NEX-03
D0012  M   56      0      -            11   NEX-02,NEX-04,NEX-06
D0013  F   54      0      -             9   NEX-05
D0014  F   60      0      -            10   NEX-02,NEX-05
D0015  F   66      0      -            10   NEX-05,NEX-06
D0016  M   19    400      -             0
D0017  M   45    401      2025-05-12    0
D0018  F   45      0      2023-04-18    8
```

| 확인한 것 | 어디서 드러나나 |
|---|---|
| 만 20세 미만은 비대상 (TGT-01) | D0016 사유코드 `400` |
| 2년 주기가 안 왔으면 비대상 (TGT-04) | D0017 — 2025 완료, 2026 예약이라 `401` |
| 2년이 지났으면 대상 (TGT-04) | D0018 — 2019·2023 중 **최근인 2023** 을 골라 대상 |
| 성별로 조건부가 갈린다 (NEX-02) | 남 D0011(만40) vs 여 D0014(만60) — 같은 Rule, 다른 기준나이 |
| 여성 전용 조건부 (NEX-05) | D0013·D0014·D0015 |
| 조건부는 최대 3종, 실제 구성 8~11종 | D0012 의 **11종**이 상한이다 (00 §7.2.2) |

| 비대상은 추가검사도 못 고른다 | D0016·D0017 은 선택 가능 AEX **0종** |

`[!]` **기대값을 문서에 적고 맞추지 않았다.** 위 표는 `UFN_HC_검진대상확인`·`UFN_HC_국가검사구성`

갖는다. 같은 값을 두 곳에 두지 않는다 (ROOT `AGENTS.md` §6).

`[!]` **2026-09-15 부터 이 갈래를 시험이 잰다.** 위 표는 그날의 **실측 기록**이고, 기대값의

## 4. 다시 돌리는 법

```bash
cd winforms
./scripts/seed-tgt-cases.sh          # 판정 갈래용 수검자 (멱등)
./scripts/seed-today.sh              # 점검용 예약을 오늘로 민다 (멱등)
MSB="C:/Program Files (x86)/Microsoft Visual Studio/2019/Professional/MSBuild/Current/Bin/MSBuild.exe"
VST="C:/Program Files (x86)/Microsoft Visual Studio/2019/Professional/Common7/IDE/CommonExtensions/Microsoft/TestWindow/vstest.console.exe"
"$MSB" HealthCheckupReservationReception.sln -p:Configuration=Debug -v:m
"$VST" tests/HealthCheckupReservationReception.Tests/bin/Debug/HealthCheckupReservationReception.Tests.dll \
       /TestCaseFilter:"FullyQualifiedName~ScenarioDbTests"
```

`[!]` **매 실행이 새 수검자를 만든다.** 주민번호 뒷자리를 실행 시각에서 만들고 차트번호는
자동발급이라, 몇 번을 돌려도 앞선 실행과 부딪히지 않는다. 대신 실행마다 수검자가 몇 명 는다 —
점검용 DB 라 그대로 둔다.

`[X]` **초판은 여기서 「몇 번을 돌려도 방해하지 않는다」고만 적었고 그것은 과장이었다.**
수검자는 겹치지 않지만 **시간대 정원 20 은 공유 자원**이다. 네 번쯤 돌리자 오늘 PM 이
20/20 이 되어 다음 실행이 통째로 `Inconclusive` 가 됐다 (2026-09-14 실측). 지금은
`[TestCleanup]` 이 그 실행이 만든 업무를 취소로 되돌리므로 정원이 제자리로 온다 — 돌린 뒤
`AM 6 · PM 3` 이 그대로였다. 이미 쌓인 것은 `scripts/cleanup-scenario-works.sh` 가 치운다.

`[!]` **마감이 지난 시각에 돌리면 접수 시나리오가 `Inconclusive` 다.** 초록이 아니고 빨강도
아니다 — 그 시각에는 접수가 막히는 것이 옳고, 그래서 **그 시나리오를 못 잰 것**이다.
판정하지 못한 검사를 PASS 로 세지 않는다.
