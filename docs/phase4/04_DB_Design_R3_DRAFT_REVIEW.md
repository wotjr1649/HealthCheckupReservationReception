## A1 `변경이력` 이 `CP-06` 을 정면 위반한다 `[HIGH]` `[Codex 단독]`

```text
00_Project_Policy.md:49
```

초안은 `04` §1.4·§1.7 의 금지조항만 수정 대상으로 잡았다(§13 대응표). **한 단계 위 `00` 의 같은 금지조항을 확인하지 않았다.**

**→ `00` CP-06 을 개정하지 않으면 `변경이력` 은 R3 에서 제거해야 한다.**

**반례 (두 검토자가 독립적으로 같은 형태를 구성)**

```text
완료이력 {2025-06-01, 2026-11-01},  예약일 2026-09-10
  R2 : CompletionDate < 2026-09-10 필터 → {2025-06-01} → MAX=2025 → 2026-2025=1 < 2 → 401 NotDue
  R3 : LastCheckupDate=2026-11-01 이 필터에 걸려 "이력 없음" → 최초검진 대상 → Eligible
```

`CompletionDate < ReservationDate` 는 **집합에 대한 필터**이고 `MAX()` 는 그 필터가 남긴 집합에 적용된다. 컬럼 하나는 필터 **전**의 값 하나만 들고 있으므로 "필터에 걸린 값을 버리고 다음 값으로 내려간다"를 구조적으로 표현할 수 없다.

초안이 `04` §5.3 의 반대를 뒤집은 논거 2개가 모두 성립하지 않는다.

| 초안 논거 | 반박 |

| *"Fixture 4행이 전부 다른 수검자라 복수 이력은 시험된 적 없다"* | **시험 커버리지의 공백**을 규칙의 부재로 바꿔치기했다. 공백은 채워야 할 결함이지 삭제 근거가 아니다 |

`[!]` 초안 §6.1.3 이 `LastCheckupDate` 에 CHECK 을 두지 않는 이유로 *"미래 완료일을 시험할 수 있어야 한다"* 를 드는데, **그 미래일을 저장하는 순간이 정확히 이 버그가 발화하는 순간**이다.

## A5 `FIN` 이 `00` 의 세 집합에서 미정의다 `[HIGH]` `[검토자1·2 · Codex]`

```text
00:123 RP-03  … `예약(RSV)`과 `접수완료(RCP)`는 각각 1건으로 산정하고 `취소(CNL)`는 제외한다
00:126 RP-06  중복판단 유효예약은 … `예약(RSV)` 또는 `접수완료(RCP)`인 업무다
00:194 TGT-02  현재 예약·접수 업무의 RSV/RCP/CNL 상태는 완료이력으로 사용하지 않는다
```

셋 다 **열거식**이라 `FIN` 에 대해 침묵한다. `04` 가 결정할 권한이 없는 값이다.

**구체적 공격** — 오늘 AM 슬롯의 `RCP` 20행을 SSMS 로 `FIN` 처리하면 `IX_예약접수_SLOT` COUNT 가 0 이 되어 같은 슬롯에 20건이 더 들어간다(**하루 40명**). 같은 원리로 `FIN` 이 된 수검자는 RP-06 재예약 차단에서도 풀린다.

**추가로 Codex 가 짚은 것**

- `FIN` 의 유일한 도달 경로(SSMS 직접 `UPDATE`)가 `04`:167 의 *"데이터 변경의 최종 권한은 Write SP"* 와 `06` §32 의 Table 권한 0 을 모두 우회한다. 허용 전이 검증이 없어 `CNR → FIN` 도 만들 수 있고 `변경이력` 에도 안 남는다
- `FIN` Work 가 있으면서 `LastCheckupDate IS NULL` 인 상태와 그 반대가 **둘 다 R3 제약을 통과**한다. 완료의 원천이 둘인데 함께 갱신하는 SP·제약·규칙이 없다

## 2.1 B1 상세 — `변경이력` 기록 지점이 Template 에서 성립하지 않는다

`06` §21.1 의 실제 제어흐름:

```text
SET XACT_ABORT ON;
-- [1] 입력검증          ← TRY 밖. 실패 시 감싸는 CATCH 가 없다
-- [2] 사전조회          ← TRY 밖. 500 WorkNotFound 로 나간다
BEGIN TRY
    BEGIN TRANSACTION;
    -- [3] applock       ← 음수 rc 면 THROW 50001 / 50002
    -- [4] 재검증
    IF @Code <> 0 BEGIN ROLLBACK; SELECT RS0; RETURN; END   ← TRY 안
    -- [5] 저장
    COMMIT TRANSACTION;                                      ← TRY 안
END TRY
BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK; THROW;
END CATCH
-- [6] 성공 RS0 + RS1    ← CATCH 밖
```

```text

  [4] 업무실패 → ROLLBACK → RS0 SELECT → 감사 INSERT(삼킴) → RETURN
```

# 9. R3 진행 방안 — `00`·`01`·`02` 개봉 승인 기준

## 9.1 게이트가 강제하는 원자성 — 세션을 나누는 기준

**한 세션에 안정적으로 담기지 않는다.** 따라서 전용 브랜치에서 중간 red 를 허용하고 **병합 시점에만 green 을 요구한다.**
