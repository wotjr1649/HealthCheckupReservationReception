흐름 한 줄

View→ 이벤트 → Presenter→ 요청 → Service→ 호출 → Repository→ SP → SQL Server
돌아오는 길은 정확히 반대다. SqlConnection 은 Repositories/ 밖으로 한 발짝도 나가지 않고, DevExpress 타입은 Views/ 밖으로 나가지 않는다.

이 구조가 지키는 규칙 여섯

① 판정은 DB 가, 표시는 화면이

정원·마감·검진대상·추가검사 가용성·저장가능 여부는 전부 SP 가 계산해 돌려준다. 화면은 그 값을 읽어 버튼을 여닫을 뿐 같은 규칙을 다시 계산하지 않는다.
예) 리본의 업무 버튼 다섯은 SP-WRK-02 RS4 허용여부 그대로다.

② 분기는 숫자 결과코드로만

모든 SP 는 첫 Result Set(RS0)으로 성공여부·결과코드·결과메시지·오류항목·서버시각 을 같은 모양으로 낸다. C# 은 DbCode enum 의 숫자로만 분기하고 메시지 문자열을 비교하지 않는다.

③ 실패 결과코드는 예외가 아니라 결과

601(행버전 충돌)·304(마감)·203(유사 수검자)은 업무 결과다. Service 의 IsSuccess 는 “DB 판정을 받아 왔는가”이고, 코드별 분기는 Presenter 가 한다.

④ 한 번 조회로 여러 섹션을 채운다

SP-WRK-02 와 SP-RSV-01 은 Result Set 여섯을 한 번에 낸다. 갈라서 부르면 서로 다른 시점의 값이 한 화면에 앉는다.
→ 데이터 공유 탭에서 어느 SP 가 어느 영역을 채우는지 본다.

⑤ 동시성은 행버전(RowVersion)으로

쓰기 SP 는 @행버전 BINARY(8) 을 요구하고, 그 사이 다른 창구가 고쳤으면 601 로 막는다. 화면은 601 을 받으면 최신값을 다시 읽어 복구한다.

⑥ SQL 은 C# 에 없다

CommandType.StoredProcedure 와 타입·크기를 명시한 Parameters.Add 만 쓴다. 인라인 SELECT 도 AddWithValue 도 없다. SP 계약은 동결이고 C# 이 맞춘다.

발표에서 짚을 세 가지

1) 계층을 지키면 시험이 쉬워진다. IXxxView·IXxxService·IXxxRepository 가 있는 이유는 단 하나 — 테스트가 가짜 구현으로 갈아 끼우기 위해서다. DB 없이 Presenter 단위시험이 돌아간다.
2) 화면 하나가 창구 둘을 겸한다. 예약 관리와 접수 관리는 같은 UcWorkbench 하나이고, 가르는 것은 WorkContext 값 하나와 그에 따라 달라지는 리본 페이지뿐이다.
3) SP 왕복을 의식적으로 줄였다. 행을 고를 때 받아 둔 한 벌(WorkDetailReadDto)을 모달에 그대로 넘겨 같은 업무를 두 번 읽지 않는다. → 호출 횟수 탭의 「아끼는 장치 넷」.

계층을 가르는 세 가지 장벽

DevExpress 는 Views/ 안에서만

IXxxView 인터페이스에는 DevExpress 타입이 나타나지 않는다. Presenter 는 GridControl 을 모르고 IList<Dto> 를 넘길 뿐이다.
게이트: scripts/verify-layering.sh

SqlClient 는 Repositories/ 안에서만

SqlConnection·SqlCommand·SqlDataReader 가 그 폴더 밖에 있으면 설계 위반이다. Form 의 이벤트 핸들러가 DB 에 닿는 길은 없다.

검증은 층마다 한 번씩만

비어 있음 = Presenter · 길이와 형식 = Service · 고유성과 동시성과 업무규칙 = DB. 같은 검증을 두 층에 두지 않는다.
에디터의 MaxLength 는 UI 제한이지 검증이 아니다.

저장 뒤 어디로 가는가는 날짜가 정한다. 예약을 저장했을 때 그 예약일이 DB 오늘날짜면 그 사람은 지금 창구에 서 있다 — 다음 할 일이 접수이므로 접수 관리로 데려간다. 미래 예약이면 다음 사람을 예약할 차례이므로 수검자 관리에 남는다. 창구마다 다를 수 있어 App.config 의 MoveToReceptionAfterSave 가 이 동작을 켜고 끈다.

버튼별 SP 호출 연결

버튼 하나를 눌렀을 때 어느 파일을 거쳐 어느 저장 프로시저에 닿는지의 전체 경로다. 경로를 클릭하면 복사된다.

버튼 있는 곳 열림 조건 View → Presenter Service → Repository 저장 프로시저
업무 버튼 다섯은 핸들러가 하나다. barBtnWorkAction_ItemClick 하나가 다섯을 다 받고, 어느 것인지는 05 §8.2 의 업무동작코드가 말한다 (EDIT_RESERVATION · CANCEL_RESERVATION · START_RECEPTION · EDIT_EXTRA · CANCEL_RECEPTION). 버튼마다 핸들러를 두면 같은 이름이 화면·Presenter·리본 세 곳에 생긴다.
모달을 여는 것은 Form 이, 열지 않는 것은 Presenter 가. [접수]·[예약변경]·[추가검사변경] 은 창을 띄우므로 MainForm 이 맡고, [예약취소]·[접수취소] 는 확인창 한 줄이라 WorkbenchPresenter 로 내려간다. UserControl 이 창을 띄우면 그 창의 부모가 화면마다 달라진다.
